# Security

## Reporting a vulnerability

Please report privately rather than opening a public issue.

Use GitHub's **[Report a vulnerability](https://github.com/TruStorey/trutools/security/advisories/new)**
button, under the Security tab. That opens a private thread visible only to you
and the maintainer.

Please don't open a public issue or a pull request for a security problem — that
publishes the details before there is a fix to go with them.

What helps, roughly in order:

- what you can do with it, in one sentence
- the request or input that triggers it
- whether it affects the hosted site, a self-hosted copy, or both
- anything you had to already have (a position on the network, a header you can set)

There is no bounty. This is a hobby project run for free. Expect an
acknowledgement within a week, and please give a fix a reasonable window before
publishing.

## Scope

**In scope** — anything in this repository, and the hosted deployment at
`tools.truvibe.dev`:

- input that escapes a tool: injection into the response, path traversal, SSRF
  out of the DNS or mail tools
- rate limiter bypass, or a way to make one caller's limit apply to another
- spoofing the address reported by `/ip`, or used as the rate limit key
- a tool that leaks data between requests, or across callers
- resource exhaustion: an input that costs the server far more than it costs you
- the usual web surface — XSS, CSRF, clickjacking, dependency confusion

**Out of scope**, and please don't file these:

- **Weak output is not a vulnerability if you asked for it.** The password
  generator will happily produce a 4-character lowercase password. That is the
  parameter you passed.
- **MD5 and SHA-1 being broken.** They are offered because real systems still
  emit them and you need to match one. The tool's page says so, next to the
  algorithm picker.
- **The JWT decoder not verifying signatures.** It cannot — it has no key. It
  states "not verified" in its own output, not just in the docs.
- **Missing rate limits on the static site.** Only the API is limited.
- Missing security headers on pages that carry no session, because there is no
  session — see below.
- Volumetric denial of service. Please do not test this against the hosted site.
- Reports generated by a scanner with no demonstrated impact.

## What the service does with your input

This is worth stating plainly, because these are tools people paste real
secrets into.

**Most tools never send anything anywhere.** The card grid runs the same
function the API runs, in your browser. Password generation, hashing, base64,
JWT decoding, subnet maths, case conversion and the rest compute locally. There
is no request to log.

**Four tools cannot work that way** and do send their input to the server:

| Tool | Why | Where it goes |
|---|---|---|
| Certificate Reader | X.509 parsing needs `node:crypto` | This server, in memory |
| DNS Lookup | needs a resolver | Cloudflare DNS-over-HTTPS, `1.1.1.1` |
| Mail Check | needs a resolver | Cloudflare DNS-over-HTTPS, `1.1.1.1` |
| What Is My IP | only the receiver knows the answer | This server |

DNS Lookup and Mail Check mean **Cloudflare sees the domain you asked about**.
That is inherent to resolving a name you don't have a resolver for. It is not
your own DNS, and it is not private.

**SSH keypairs are generated in your browser** with WebCrypto. The private key
is never transmitted. The `/ssh-keypair-generator` API endpoint exists for
`curl` and does generate server-side — if you use it, you are sending a private
key over the wire, which is fine for a throwaway key and wrong for a real one.
Use the browser tool, or `ssh-keygen`.

**The SSH Key Inspector refuses private keys** rather than parsing them, and
runs locally regardless.

**What is logged.** Tool inputs are not written to logs. The server logs
unexpected handler errors (`console.error` with the thrown error) and Redis
connection problems. An error thrown deep inside a parser could in principle
carry a fragment of the input in its message, so this is "not logged on
purpose", not a cryptographic guarantee. There is no analytics and no request
body persistence. The site sets **no cookies at all** — the only thing it keeps
in your browser is the light/dark preference, in `localStorage`, via
`next-themes`.

**What Redis stores.** One sorted set per caller IP, holding the timestamps of
that IP's recent requests, expiring after the rate limit window (60 seconds by
default). Addresses, no payloads.

## Design decisions that look like bugs

Each of these is deliberate. If you think one is wrong, that is a discussion
worth having — file an issue rather than an advisory.

**The rate limiter fails open.** If Redis is unreachable, requests are allowed
rather than refused. A public utility API going dark because its limiter is
sick is a worse outcome than a window without limiting.

**The caller's IP is the rightmost publicly routable entry in
`X-Forwarded-For`.** A route handler cannot see the socket peer, so this
recovers what icanhazip gets for free. Scanning from the right skips our own
private proxy hops, and a caller cannot move it, because they can only prepend
entries on the left.

**Behind a CDN, that is not enough**, and `CLIENT_IP_HEADER` exists to name a
header to trust instead — `cf-connecting-ip` in the hosted deployment. **A
trusted header is only safe if the origin cannot be reached directly.** If you
self-host with `CLIENT_IP_HEADER` set and your origin is exposed, anyone can set
that header and both spoof `/ip` and choose their own rate limit bucket.
Restrict the origin to your CDN's ranges, or leave the variable unset.
[`docs/self-hosting.md`](docs/self-hosting.md) has the detail.

**The DNS and mail tools cannot be pointed at an arbitrary host.** They talk to
one hardcoded DoH endpoint; the user-supplied part is a domain name in a query
string, never a URL. That is the SSRF guard — there is no address for a caller
to substitute.

**API responses carry `X-Robots-Tag: noindex` and `Cache-Control: no-store`.**
Tool endpoints sit at root-level URLs, which crawlers will index; a generated
password sitting in a search result would be a bad day.

**CORS is wide open** (`Access-Control-Allow-Origin: *`). It is a public,
unauthenticated, read-only API — there is nothing for a cross-origin request to
abuse, because there is nothing a browser holds that would make one privileged.

## Supported versions

The deployed `main` branch. There are no released versions and no backports; if
something is wrong, it is fixed on `main` and redeployed.
